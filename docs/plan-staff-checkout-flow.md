> 2026-09-20 制定。起因是业主一句「结账什么的，员工的操作都很复杂，绕来绕去的」。
> 本文只定方案，**不含代码改动**。所有结论都对着当前工作树（`482aa59`）的代码核过，
> 引用的行号以那一版为准。
>
> **进度**：第一批（后端自动带明细 + estimatedCents）已上线并部署，见提交 `aee5b0a`。
> 第二批（结账合成一页）已实现，见下方「第二批实施记录」。第三、四批未开始。
>
> 与本文相关的既有约束：金额整数分；权限后端判；已付订单不可改（迁移 003 触发器）；

## 0. 现状：绕在哪儿

### 0.1 一个模型，两套规则，两套界面

后端其实**只有一种会话**：`store.sessions` 里全是 `tablesdomain.Session`，顾客扫码申请
确认后生成的会话也在这里，只是多了一个 `AdmissionID`（`membership.go:562`）。
「两套」不是模型分裂，是**规则和界面**分裂：

| 分叉点 | 代码 | 后果 |
|---|---|---|
| 带 `AdmissionID` 的会话，`/venue-sessions/{id}` 上任何非 GET 一律 409「请从会员计时工作台操作此体验」 | `tables.go:266` | 桌位页点一张扫码开的桌，进会话页，暂停/续时/换桌全部点不动 |
| 套餐订单不能改明细、不能人工折扣 | `orders.go:230` | 结账页对这类订单是只读的，但页面不知道，照样画出编辑控件 |
| **订单带账户 + 门店有任何已发布规则 → 普通收款一律 409**「请使用会员结账预览并确认收款」 | `orders.go:225` | 店里已发布「1 小时」套餐，所以**所有注册顾客**在结账页点「确认已收款」都会在最后一步被打回，必须去另一页 |
| 桌位会话建单**一行明细都没有** | `orders.go:107` | 店员进结账页看到白单，要在「自定义服务」里手打「计时收费 29.90」；系统明知道计了 60 分钟、明知道套餐 ¥29.90 |
| 扫码申请的订单**自动带套餐行** | `membership.go:562,638` | 同一件事两条路一条自动一条手打 |

### 0.2 一次结账要经过的页面

```
桌位 tab ─┬─ 点桌（店员开的）──▶ 会话页 ──「核对订单并结账」──▶ 结账页 ─┬─ 散客：填明细→保存→选方式→确认
          │                                                          └─ 会员：「会员结账」──▶ 会员与计时 › 结账 tab ──▶ 预览→再选一次方式→确认
          └─ 点桌（顾客扫码开的）──▶ 会话页（暂停/续时/换桌全 409，死胡同）

工作台「计时开台」──▶ 会员与计时 › 计时 tab ──▶ 在全店申请列表里找 ──▶ 确认开台 / 结账（切到结账 tab）
```

「会员与计时 › 结账」这个 tab 自己没有门：直接点进去是一句「请从计时工作台或订单结账页
选择账单」。它只能被别的页面「送」进来。

### 0.3 点击数（三种最常见的单）

| 场景 | 现在 | 目标 |
|---|---|---|
| 散客整桌 60 分钟 | 桌位→点桌→会话页→结账页→添加明细→选「自定义服务」→填名称→填单价→保存明细→选方式→确认已收款：**5 屏 · 11 步 · 手打 2 个字段** | 桌位→点桌→会话页（已显示应收 ¥29.90）→去收款→选方式→确认：**3 屏 · 5 步 · 0 手打** |
| 会员整桌 60 分钟 | 上面全部 + 「会员结账」→切页→预览→再选一次方式→确认：**6 屏 · 15 步**；且若店员在结账页直接点「确认已收款」会得到一条 409 错误 | 同散客 + 页内的积分/余额两个开关：**3 屏 · 6 步** |
| 顾客扫码申请 | 开台：工作台→会员与计时→计时 tab→列表里找→确认；结账：同一条路再走一遍→「结账」→切 tab→预览→选方式→确认：**两趟各 4–5 步**；桌位页点这张桌是死胡同 | 开台：工作台「待确认申请 1」→确认：**2 步**；结账：同散客那条路 |

## 1. 目标形态

**一张桌一个入口，一张单一屏结清。**

- 不管这单是店员开的还是顾客扫码申请的，店员都从**桌位页点那张桌**进去，看到同一个会话页。
- 会话页直接显示**应收多少**（后端按时长和已发布套餐算好），店员报价不用先建单。
- 结账页是**唯一**的结算屏：明细（多半是自动带好的）、会员抵扣（有账户才显示）、收款方式、
  **一个**「确认收款 ¥X」。
- 「保存明细」这一步消失：改了明细就在确认时一起提交，版本冲突当场重读。
- 「会员与计时」瘦成 **会员 / 申请 / 规则**：「计时」tab 只留待确认的申请和桌码工具，「结账」tab 删掉。

后端的 409 守门（`orders.go:225,230`、`tables.go:266`）**前三批都不拆**。它们是安全网，
界面收拢完了它们自然不再被触发；第四批再把规则合到同一组处理器里。

## 2. 分批

### 第一批 · 后端：账单不再空白（约 1 天，含测试与部署）

**A1. 桌位会话建单时自动带计时行**（`orders.go:107` 附近）

```
timed 且时长 == 某已发布套餐.DurationMinutes
    → Line{Name: 套餐名, Quantity: 1, UnitPriceCents: 套餐.AmountCents}
timed 且时长 == 套餐.DurationMinutes + k × 套餐.RenewalMinutes（k ≥ 1，RenewalMinutes > 0）
    → 套餐行 + k 行「套餐名 · 续时」（照 membership.go:638 的写法）
timed 但对不上任何套餐 / free（自由计时）
    → Line{Name: "计时 N 分钟" 或 "自由计时 · 已用 N 分钟", Quantity: 1, UnitPriceCents: 0}
      —— 名字和时长带上，价留空给店员填。**不编价**：收费政策没定（见第 6 节第 1、2 条）。
```

- 只在**新建**订单时生成；订单已存在（`orders.go:79-90` 那条「当前会话已有草稿返回同一订单」）不动。
- 「已用 N 分钟」按 `Session.Deadline`/`StoppedAt`/`PausedSeconds` 算，与 `tables.go:141-148` 同一套口径，不另写一份。
- 匹配用 `s.store.membership.Rules()` 里 `kind == "package"` 且已发布启用的；一个时长命中多个套餐时取
  `AmountCents` 最低的（对顾客有利，且可预期），并在审计里记下命中了哪个。
- 契约：`docs/api.yaml` `createOrder` 的 201 描述加一句「桌位会话建单按时长自动带计时明细，
  未匹配套餐时单价为 0 待填」。响应结构不变。
- 测试：`internal/app/` 新增 `order_autolines_test.go` —— 60 分钟命中「1 小时」；90 = 60 + 30 续时；
  45 分钟无套餐 → 0 价占位行；free → 占位行；已有草稿不重生；套餐停用后不再命中。
  改了写路径 → `make backend-test-db`。
- 部署：无迁移（`Order.Lines` 是 JSON state），照 2026-09-19 的流程：pg_dump → 留旧二进制 → 换 → healthz/readyz → 20 张桌。

**A2. 会话视图带「预计应收」**（`tables.go:130-160` 的 `view`）

- 给 `/service-tables` 每张桌的视图加 `estimatedCents`（按 A1 同一套匹配算，会话进行中也算得出），
  会话页据此显示「应收 ¥29.90」而不必先建单。
- 对不上套餐时为 `null`，前端显示「按时长 N 分钟，结账时填价」。
- 契约：`ServiceTable` schema 加可选 `estimatedCents`。

**不做**：不动 `orders.go:225` 的 409。第二批前端合页之后它就不会再被点到；留着是安全网。

### 第二批 · 前端：结账合成一页（约 2 天）

**B1. 结账页吸收会员抵扣**（`pages/staff/checkout/index.tsx`）

- `order.accountId` 有值时，页面多一段「会员抵扣」：可用积分、积分输入、余额开关、
  「预览」按钮 → 报价明细（会员优惠 / 积分抵扣 / 余额支付 / 线下补付）。逻辑从
  `membership/checkout.tsx` 的 `CheckoutTab` 抽成 `components/staff/member-settlement.tsx`，
  数据走现有 `loyalty.action({action:'quote'|'checkout'})`，不加接口。
- 打开页面若有账户就**自动预览一次**（积分 0、不用余额），店员什么都不选也能直接收线下款——
  这对应 `orders.go:225` 那条 409 想逼出来的路径，现在它成了默认路径而不是报错。
- 收款按钮按情况调不同接口：有账户 → `checkout`（带 `quoteVersion`）；无账户 → `payOrder`。
  店员看到的是同一个按钮。
- 删掉页顶那个「会员结账 · 积分与余额」大按钮（它就是跳去另一页的那一跳）。
- `membership/index.tsx` 的 `orderId` 深链保留为**重定向**：`membership?orderId=X` → `checkout?id=X`，
  旧入口不断。

**B2. 明细区按「多半是自动带好的」重画**

- 自动行显示为普通一行「1小时 ×1 ¥29.90」，右侧「改」才展开编辑控件；「添加明细」保留给零售商品。
- 0 价占位行高亮并写「请填单价」，确认按钮在它填好之前置灰并说明原因。
- 套餐订单（`session.admissionId` 非空）明细只读，页面写明「套餐订单按购买快照结算，其他消费另建单」——
  这句话现在只在后端 409 的文案里，店员点了才看到。

**B3. 保存与收款合成一步**

- 一个按钮「确认收款 ¥X」。有未保存改动时：先 `updateOrder(lines, version)` → 用返回的新版本
  接着 `payOrder`/`checkout`。一次点击，两个请求串行。
- 任一步 409：就地重读订单，画出「你的改动 vs 最新」，一个按钮「按最新重新确认」。
  不再让店员在「重新读取订单」和「重新预览」两处分别处理。
- `docs/product.md:34`「付款前须保存明细」改为「确认收款时一并提交明细，版本冲突当场重读」。

**B4. 会话页对两种来源一视同仁**（`pages/staff/session-detail/index.tsx`）

- 顶部加「应收 ¥X」（来自 A2 的 `estimatedCents`），店员报价不用进结账页。
- `session.admissionId` 非空时，暂停/继续/续时/换座走 `loyalty.action`（`pause/resume/renew/move`，
  现有动作），而不是 `/venue-sessions` PATCH——`tables.go:266` 那条 409 就不会被撞上。
  「撤销未结账会话」对套餐订单隐藏（产品规则：实际消费免收须授权留原因，不能当误开撤销）。
- 「核对订单并结账」改名「去收款」：仍是建单（或取已有草稿）后进结账页，但按钮上先写着金额。
- 桌位页点一张扫码开的桌，从此不再是死胡同。

**B5. 「会员与计时」瘦身**（`pages/staff/membership/`）

- tab 变成 **会员 / 申请 / 规则**。
- 「申请」= 原「计时」tab 去掉进行中会话的操作区（那些搬去会话页了），只留：待确认申请列表（确认 / 拒绝）
  + 桌码生成与复制。桌位布局那个 `Switch` 平铺图删掉——桌位页已经是平面图。
- 「结账」tab 删除。`CheckoutTab` 组件移到 B1 的位置。

测试：`membership.test.cjs` 里结账相关用例迁到新组件；`responsive.test.cjs` 会话页两种来源各一条；
`ui-workflows.test.cjs` 加「一次点击 = 保存 + 收款」和「409 后按最新重新确认」两条；
`navigation.test.cjs` 加 `membership?orderId=` 重定向。

## 4. 不做的

- **不编收费政策**。45 分钟、自由计时、陪客怎么收，`docs/product.md:155` 第 4 条明说还没定。
  A1 遇到对不上的时长就留 0 价占位行让店员填，不按比例折算，不按分钟乘单价——那是替业主做决定。
- **不动退款**。退款登记留在订单页，这次不搬。
- **前三批不拆后端 409**。它们挡的是「绕过会员权益直接收款」和「改套餐快照」两件真事；
  界面收拢完之后它们不会再被点到，第四批再合并处理器。
- **不改会话模型**。`AdmissionID` 这个标志继续当「按套餐快照计价」的标记用；不新增表、不迁移。
- **不给结账页做「多人合付」**。产品文档里它和收费政策一起待定。

## 5. 风险

- A1 自动行的价来自**建单那一刻**已发布的套餐。套餐改价后，已建的草稿不跟着变——这是对的
  （和扫码申请的「套餐快照」同一逻辑），但要在结账页写明「按开台时套餐计价」，否则店员会以为算错。
- B3 一次点击两个请求：第一步成功第二步失败时，订单明细已保存而款未收。页面要如实显示
  「明细已保存，收款未完成」，按钮变成只做第二步，不能让店员以为整单都没提交。
- B4 把套餐会话的操作接到 `loyalty.action`：这些动作要 `expectedVersion`（会员视图版本），
  会话页现在没拉会员视图，要多一次 `loyalty.staff()` 读取。5 秒轮询下的版本竞争
  用现有「计时已变化，请刷新后重新确认」文案兜。

## 6. 业主已定（2026-09-20）

1. **30 / 90 / 120 分钟怎么收** —— 业主让我定。**决定：代码里一律不编价。**
   建单时只做「查表」不做「算价」：时长正好等于某个已发布套餐就带那个套餐的行；
   等于套餐加若干次续时（且套餐配了续时方案）就带套餐行加若干条续时行；
   对不上就留一条 0 价占位行写清时长，由店员填。
   理由：价是经营决定，不是代码能推的。按分钟折算听着合理，但它等于替业主定了
   「30 分钟 = 半小时价」这条政策，而业主并没有这么说过。
   业主随时可以在「规则」里把 30 / 90 / 120 发布成套餐，或给「1 小时」配上续时方案
   （`renewalMinutes` / `renewalCents`），那一刻这几档就自动带价了，**零代码**。
2. **自由计时** —— 暂时手填。带一条 0 价占位行，名字里写清已用多少分钟。
3. **会员不使用积分余额时允许直接收线下款** —— 允许。B1 据此在打开结账页时
   自动预览一次（积分 0、不用余额），店员什么都不选也能直接收款。
4. **陪客** —— 暂时不收。带一条 0 价的「陪客」行，让它出现在账单上但金额为零；
   收费政策定了再改这一处。

第 1、2、4 条合起来就是一条规则：**匹配得上套餐才有价，匹配不上就留空给人填。**
