# 计划：会员储值消费登记、智能豆板次数与店员代开会员

> 2026-10-27 制定。背景：门店已经有几位充值会员，老板现在纯手工记账，每次消费后自己算好余额、用微信发给顾客。
> 系统内收费关着（钱在美团、大众点评收），储值只能靠「手动加减」，记出来的样子和老板要的差得远。
>
> **进度**：2026-10-27 方案与第 1 节的各项决定已由业主确认；同日后端、网页后台、小程序与顾客网页已实现（没有迁移，新字段都写在流水和账户的 state 里）；后端、网页后台和顾客网页 2026-10-27 随 0.0.33 上线，小程序 0.0.33 只传了体验版。
> 第 2.8 节「复制给顾客」随 0.0.34 上线（2026-10-27，网页后台已可用，小程序端只在体验版）。还没做：第 2.9 节「消费提醒」（等老板选模板）；小程序真机验收与提审；业主过目隐私协议新加的那句；发布两个充值方案；补录老会员的账（见 `docs/product.md` 待办 17）。

## 0. 老板现在怎么记

- 两个充值方案：充 500 送 88、充 888 送 120，另送智能豆板次数（888 那档送 2 次；104 智能豆板平时 10 元/小时、30 元封顶）。当时没做次卡，是因为分工作日周末、用不用智能豆板，要分出六七八种卡。
- 每次来按价目扣钱（单人或双人、工作日或节假日、几小时），用了智能豆板就扣一次赠送次数。
- 老板发给顾客的一条记录（去掉了称呼和手机号）：

  ```
  充值 888 得 1008 + 2 次智能豆板
  10 月 25 日
  1008 - 79.9 = 928.1，余额剩 1 次智能豆板
  ```

- 现在用「手动加减」记，差在：会员卡上是「储值本金」「赠送余额」两个数，不是一个余额；明细每条都叫「资产调整」，时间是录入那天；智能豆板次数没有地方放，只能写在原因里；金额、扣本金还是扣赠送都要店员自己算。

## 1. 已定（2026-10-27 业主）

| 事项 | 决定 |
|---|---|
| 哪档送豆板 | 充值方案里的一项设置，老板在网页后台「经营规则」给每一档填送几次（0 不送），不写死 |
| 豆板次数过期 | 不过期 |
| 一次用几块 | 消费登记时店员填次数（0、1、2……），双人可能用两块 |
| 余额显示 | 合成一个数，小字写其中赠送多少 |
| 金额来源 | 店员按价目手填；会员价目表自动带价以后再说 |
| 余额不够 | 扣光余额，差的在系统外收，明细写「余额不够，另付 ¥X」 |
| 老会员的账 | 逐笔补：先补充值，再按日期补每次消费 |
| 补录日期 | 不限；超过 7 天的只有店长、老板能登记（店员只能选最近 7 天，防手滑选错） |
| 撤销消费 | 店长、老板 |
| 代开会员 | 所有员工 |
| 撞号 | 小程序自己注册时填的号撞上还没绑微信的账户（代开的或网页注册的）：拦下，提示找店员要临时密码认领，不另建新号 |
| 认领入口 | 小程序登录页放一行「店里已经帮我开过会员」 |

## 2. 方案

### 2.1 余额合成一个数显示

- 会员卡上大字是「余额」= 本金 + 赠送余额，下面小字「其中赠送 ¥120.00」（没有赠送时不写）。员工两端的会员卡同样。
- 后台照旧分开记本金和赠送：充值退款要整笔退本金、收回赠送，会员结账退款按比例退回各自账户，这些规则不变。

### 2.2 智能豆板次数

- 新的一项会员资产，和余额、积分一样只能经流水变动：充值方案赠送（+）、消费登记用掉（−）、手动加减（±，写原因）、撤销消费退回、充值退款时收回这笔充值送的。扣不成负数，不过期。
- 不能单独买，只随充值方案送或由店员手动加，所以不是次卡；`docs/product.md` 的「不做次卡」补这句说明。

### 2.3 充值方案附送次数

- 充值方案加一项「送智能豆板 N 次」（0 表示不送），老板照旧保存草稿、发布；已发布的旧方案不受影响（视为 0）。
- 店员用「充值登记」入账，本金、赠送余额、次数一次到账。

### 2.4 会员消费登记（新）

- 入口：小程序员工「会员」页、网页后台「会员资产」，选中顾客后点「消费登记」；所有员工都能办。
- 填：
  - **日期**：默认今天（门店日期），可以往前选；店员只能选最近 7 天，更早的店长、老板能选。不能选将来。
  - **内容**：时长从已发布的套餐里选（1 小时、2 小时、3 小时、全天不限时），另有「其他」；单人或双人；工作日或节假日（按星期默认，周六日算节假日，法定节假日店员手动改）。
  - **金额**：元，店员按价目填，可以是 0（只用豆板次数时）。
  - **智能豆板**：用掉几次，默认 0；不能超过剩余次数。没有次数了的豆板费由店员算进金额。
  - **备注**：选填，「其他」时必填。
- 扣钱先扣本金、再扣赠送余额（同会员结账）。余额不够时扣光余额，差额记为「另付」（只是记录，钱在系统外收）。
- 确认框写清：扣多少（本金、赠送各多少）、另付多少、豆板用几次、扣完余额与剩余次数。
- 记一条「消费」流水，存下日期、内容、金额、本金和赠送各扣多少、另付、用掉的次数、备注，以及**记完这一笔的余额和剩余次数**（存下来，以后改算法也不变）。
- 资金写操作：带顾客会员资产的版本和 `Idempotency-Key`，记审计（谁、给谁、扣多少，不写手机号）。
- 登记错了：店长、老板在网页后台「会员资产」对那一条「撤销」（小程序员工端只显示已撤销），写原因，生成一条反向流水（退回本金、赠送和次数），原记录标「已撤销」留着。一条只能撤销一次。

### 2.5 顾客的明细

- 每条显示：日期（消费、充值登记时选的那天；其他流水是记账那天）、标题（「消费 · 单人 3 小时 · 节假日」「充值 · 888 送 120」「门店调整」）、金额、智能豆板 ±N、记完这一笔的余额和剩余次数；另付、备注、撤销原因有就显示。
- 按记账先后排；补录时按日期从早到晚录，余额才是一路接下来的。

### 2.6 补录以前的账

- 充值：「充值登记」加「充值日期」（默认今天，补录规则同消费登记）。现在没有充值的营业额报表（导出只有订单、退款、采购、库存流水），往前记不影响别的数。
- 消费：用消费登记，选当时的日期。
- 几位老会员按老板的手工账逐笔补：先补充值，再按日期补每次消费；补完余额应和老板手里的数一致。

### 2.7 店员代开会员

- 小程序员工「会员」页、网页后台「会员资产」加「代开会员」：填称呼、手机号（同网页注册的校验：去掉空格和横线后 6～15 位数字），勾「顾客已同意门店记下称呼和手机号」。这个号已经有账户（不论怎么注册的）时不新建，直接打开那个账户。所有员工都能办，记审计。
- 代开的账户没有微信、也没有网页登录，顾客暂时登不进去，但店员能给它充值、登记消费。
- 顾客怎么看到自己的账：
  - 顾客网页（当时也能用临时密码登录）2026-10-31 下线，店员给的临时密码只用来在小程序认领，员工那边的按钮改叫「发临时密码」。
  - **小程序（新）**：登录页加一行「店里已经帮我开过会员」：填手机号和店员给的临时密码（也可以是这个号的网页密码）、同意隐私协议，这个微信就绑到那个账户上，并补上本人同意隐私协议的记录。临时密码和网页是同一个（24 小时内有效），认领用掉后作废，顾客要用网页时再找店员重置。这个微信已经注册过别的账户时拒绝认领。
- 小程序自己注册时填的手机号撞上**还没绑微信的账户**（代开的，或在顾客网页注册的）：不另建新号，提示「门店已经用这个手机号为你开过会员，请找店员要临时密码，在登录页点『店里已经帮我开过会员』认领」。
- 隐私协议加一句：门店可以替你开会员，记下你告诉店员的称呼和手机号（措辞给业主过目）。

### 2.8 复制给顾客（2026-10-27 业主定）

老板现在每次消费后自己算好、用微信发给顾客。登记成功后和会员流水里，消费、充值两种记录给一个「复制给顾客」，复制下面这样的文字，店员贴到微信里发：

```
EXAMPLE 示例工坊 · 消费记录
10月25日 单人 · 3 小时 · 节假日
消费 ¥79.90，余额扣 ¥79.90
余额 ¥928.10（其中赠送 ¥120.00）
智能豆板用 1 次，剩 1 次
```

```
EXAMPLE 示例工坊 · 充值记录
10月25日 充值「888 送 120」
付 ¥888.00，到账 ¥1,008.00，送智能豆板 2 次
余额 ¥1,008.00（其中赠送 ¥120.00）
智能豆板剩 2 次
```

- 日期用这一笔的业务日期（`serviceDate`，写成「10月25日」，不是今年的写上年份），余额和次数用这一笔记完时存下的（`balanceAfter`），不按现在的余额算。
- 余额不够时多一行「余额不够，另付 ¥50.00」；没用豆板时写「智能豆板剩 1 次」；赠送为 0 时不写括号；备注不复制（那是写给店里看的）。
- 已撤销的消费不给复制。网页后台用浏览器剪贴板，小程序用 `setClipboardData`，复制后提示「已复制，去微信粘贴给顾客」。

### 2.9 消费提醒（微信订阅消息，2026-10-27 业主定）

消费登记成功后，给允许过的顾客发一条微信订阅消息，内容同上：日期、内容、消费金额、记完的余额、豆板剩几次（另付有就写）。

- **只在消费登记后发**（业主定）：充值、撤销、手动加减都不发。微信的一次性订阅是顾客允许一次只能发一条，发在别处，当天消费那条就发不出去了。
- **在哪允许**（推荐，可再改）：小程序里点「提交预约」时和预约的三种放进同一个订阅框；扫桌码「申请入座」提交时；会员中心「开启消费提醒」（写明还能收几次）。顾客拒绝照常办事，不追问。
- **记次数**：顾客每允许一次记一次（存在库里，每个账户最多攒 10 次，多了不记），消费登记时用掉最早的一次。和预约通知一样，允许时带新的登录码换 openid、核对、加密存下（同一套 `PINDOU_WECHAT_OPENID_KEY`，没配就整个关着）。
- **发送**：登记消费的事务里领一次、备好内容，提交后再调微信；失败只记错误码，不重试。店员两端那条消费上标「已微信通知」或「通知没发出去」，没允许过的什么都不标，店员看着决定要不要手动复制发。
- **模板**：要老板在公众平台「订阅消息 › 公共模板库」（类目休闲娱乐）选一个一次性订阅模板，关键词最好有消费时间、消费内容（或项目）、消费金额、当前余额、备注（或温馨提示）。模板编号和关键词写死在代码里（同预约通知），**选好之前这项功能关着**：不弹框、不发。未确认：休闲娱乐类目下有没有这类模板。

## 3. 要改的地方

- **后端**：流水加业务日期、智能豆板次数、消费明细、另付、记完的余额与次数（写进流水的 state，按 omitzero 保证旧流水的版本不变，能不加迁移就不加）；`/loyalty/actions` 加消费登记、撤销消费，充值登记加日期，手动加减加次数，充值方案加赠送次数；会员视图的余额加次数；员工代开会员；小程序认领；小程序注册撞号拦截；网页首次登录补同意。`docs/api.yaml` 同步；动了迁移就配隔离库集成测试。
- **网页后台**：「会员资产」页的余额显示、消费登记、撤销、代开会员、充值日期、手动加减次数、流水显示；「经营规则」充值方案的赠送次数。
- **小程序**：员工「会员」页同上；顾客会员中心的余额、次数、明细；小程序登录页认领（新页面按 `.claude/skills/mp-add-page` 走）。
- **文档**：`docs/product.md` 的会员、账户与「不做次卡」说明。

## 4. 不做

- 不接微信在线支付，不卖次卡，不按计时自动算钱（收费开关关着）。
- 不做会员价目表自动带价（以后再说）。
- 充值、撤销、手动加减不发微信通知（只有消费登记发，见 2.9）。
