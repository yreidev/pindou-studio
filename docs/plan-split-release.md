# 顾客网页下线、网页后台单独部署、各端各自发版

2026-10-31 业主定：小程序能正式上线了，顾客网页（pindou.example.invalid 上给顾客用的页面）下线；员工网页后台（admin.example.invalid）照常用，改成和后端分开部署；后端、网页后台、小程序各有各的版本号和发版标签。三者仍在同一个仓库。

## 一、顾客网页下线

不变的：

- pindou.example.invalid 这个域名和证书照旧：小程序接口 `https://pindou.example.invalid/api/v2` 就在这个域名上。
- 网页桌码（普通二维码 `https://pindou.example.invalid/t?tableId=…`）照常用：微信「扫一扫」或长按识别命中已发布的「扫普通链接二维码打开小程序」规则，直接打开小程序入座页，不经过网页。微信的校验文件仍由后端在域名根目录和 `/t/` 下提供。微信官方文档没写规则发布后能不能删校验文件（未确认），按一直保留处理。网页后台「桌码」页照样生成网页桌码，已经印出去的照常能用。
- 员工代开的会员，以及在顾客网页注册过的账户，照旧在小程序登录页「店员帮我开过会员，去认领」里用手机号加员工发的临时密码认领；以前在网页设过密码的，填那个密码也行。员工发临时密码的入口（网页后台会员页、小程序员工会员卡）保留，改叫「发临时密码」，说明只讲认领。

变的：

- 不用微信扫网页桌码（手机相机、浏览器、支付宝）：以前打开顾客网页的入座页，现在打开一页「请用微信扫码」的说明。这一页由后端直接给，不带脚本。
- 去掉网页注册、手机号加密码登录、改网页密码三个接口（`/auth/phone-registrations`、`/auth/phone-sessions`、`/auth/password-changes`，访问返回 404）。顾客网页的会话（`auth_sessions.client = 'h5'`）一律当无效：不能让它被当成小程序会话、按真实任命给权限。
- 删掉小程序代码里的网页版分支和网页专用页（密码登录、改密码、网页隐私协议）、`build:h5` 和嵌入脚本，后端的 `internal/customerweb`，以及网页后台端到端里的顾客网页用例。
- 数据：`account_passwords` 留着，认领要用。已有的 h5 会话和 `auth_sessions.client` 的检查约束这一版不动：滚动发布时旧版本还在发 h5 会话。

## 二、网页后台单独部署

- 网页后台单独一个镜像 `docker.io/yreidev/pindou-admin`。镜像里是一个只提供页面的小 Go 程序（`cmd/pindou-admin-web`），页面由 go:embed 编进去，复用 `internal/webui` 的托管方式：内联脚本按哈希放行的 CSP、带哈希的文件长期缓存、其余路径回 index.html。它不连数据库，也不调微信。
- 后端镜像只剩接口，不再嵌入任何页面。在顾客域名下，后端只提供校验文件和「请用微信扫码」那一页；其余不是接口的路径一律返回 404。
- 地址不变：admin.example.invalid 上的 `/api/` 和 `/healthz` 由 Traefik 转给后端，其余转给网页后台服务。页面和接口仍然同源，不用配跨域。
- 托管页面用 Go 不用 nginx，有两个原因：
  - CSP、缓存、回退的写法和测试已经在 `internal/webui`，换 nginx 要另抄一份 CSP；
  - 用同一份代码，端到端测的就是线上的托管方式。
- 本机开发和端到端照旧由 `cmd/pindou-dev` 在同一端口同时提供接口和网页后台页面。
- 网页后台首页「系统状态」显示网页后台自己的版本和 commit（构建时写进页面）、后端版本（读 `/healthz`），以及「小程序正式版（最近使用）」和上报时间。小程序版本由已登录员工的正式版小程序在登录后和回到前台时自动上报，后端持久化最近一次记录，网页收到更新后刷新；开发版、体验版不上报。手机可能尚未更新，所以这不代表微信当前最新发布版本；没有上报记录时显示「尚未收到」，读取失败另行提示。小程序版本显示已实现、待发布（迁移 029），此前上线的 0.0.39 只有前两行。
- 部署清单 `deploy/k3s/pindou.yaml` 加了 pindou-admin 的 Deployment、Service、网络策略，admin.example.invalid 的路由拆成两条（`/api/`、`/healthz` 优先给后端）。外部巡检 `deploy/monitor.sh` 对顾客域名改成查「请用微信扫码」那一页。

## 三、各端各自的版本号和标签

| 端       | 版本号写在                                | 标签              | 打标签后                                     |
| -------- | ----------------------------------------- | ----------------- | -------------------------------------------- |
| 后端     | 标签本身（编进二进制，`/healthz` 显示）   | `backend-v0.0.39` | 构建 `pindou-api` 镜像                       |
| 网页后台 | `pindou-admin/package.json` 的 `version`  | `admin-v0.0.39`   | 构建 `pindou-admin` 镜像，版本须与标签一致   |
| 小程序   | `pindou-miniapp/package.json` 的 `version` | `miniapp-v0.0.39` | 上传体验版，版本须与标签一致                 |

- 三端都从 0.0.39 起各自往上加。改了哪端就只给哪端打标签、只发哪端。
- 旧的 `v0.0.x` 标签留作历史，不再触发任何流程。
- 镜像仍然只在这个提交在 main 上的「工程验证」通过后才构建，生产仍然手动上线、上线前先备份。
- 分开发版以后，新后端要兼容线上正在用的网页后台和小程序：接口只增不改，同迁移的规矩。前端要用新接口的改动，等后端先上线再发。

## 四、第一次上线的顺序

1. 小程序：正式版要带认领入口，顾客网页才能下线，不然店员代开的会员和在顾客网页注册过的顾客进不了自己的账户。线上正式版已是 0.0.38（0.0.33 起都有认领入口），这一条已满足。0.0.39 带这一批改动，打 `miniapp-v0.0.39` 上传体验版、提审，不用等后端。
2. 网页后台：打 `admin-v0.0.39` 出镜像，部署 pindou-admin 服务和新路由，确认 admin.example.invalid 正常（扫码登录、首页两行版本）。这时旧后端 0.0.36 还嵌着页面，只是不再有请求转给它。2026-10-31 已部署（先建服务、就绪后再切路由）。
3. 后端：1、2 都完成后，打 `backend-v0.0.39`，备份数据库，再发不带页面的新后端。2026-10-31 已部署，顾客网页已下线；`/t` 返回「请用微信扫码」，旧顾客网页和退役的密码登录接口返回 404，微信校验文件保留。

这一批的网页后台和小程序配旧后端 0.0.36 也能用：续时方案、入座申请的失效时刻是新加的可选字段，旧后端不给时，整桌续时只能自己填分钟，入座申请不写几点失效。
