# 后端改为以 PostgreSQL 为准（计划与进度）

## 为什么改

0.0.6 之前，后端把全部业务数据放在进程内存里，每次写把内存序列化后落库。0.0.6 改成只写有变化的记录，解决了「数据越多写越慢、最后写不进去」，但留下几件根上的问题：

- 每次写仍要把整份内存序列化两遍（回滚点和找出改动），耗时随历史数据缓慢增长；全部历史也一直留在内存里。
- 状态在进程里，只能跑一个副本：发布约 7 秒不可用，进程出问题就是整店停摆；全局写锁让所有请求排队。
- 回滚靠整份 JSON 往返，`json:"-"` 的字段会丢；panic 时可能带走锁。
- 员工端好几个接口一次下发全部账户、全部预约，会员余额要扫全部流水。

## 目标

1. **每个请求一个数据库事务**：写请求用 SERIALIZABLE，冲突时整个请求自动重试；读请求用只读快照。请求只读写它涉及的记录，进程不持有业务状态，也没有全局锁。
2. **记录格式不变**：每张表的 `state` 列仍是现在的 JSON，旧数据不用迁移，不可改写触发器照常生效。
3. **实时推送走 PostgreSQL 的 LISTEN/NOTIFY**：写事务里 `pg_notify`，提交后才送达（回滚的写不会推送），每个副本各自监听再推给自己的连接。不加 Redis：它的发布不跟事务走，提交失败也照样推出去，还多一个要部署、备份、监控的组件；这里只有一家店、两个副本，PostgreSQL 足够。
4. **登录会话、扫码登录挑战、限流计数、幂等记录都在库里**，任何一个副本都能处理任何请求。
5. **两个副本滚动更新**：发布不停机，一个副本出问题另一个照常服务。迁移在咨询锁里执行，只做向后兼容的改动（先加后删），新旧版本能同时跑。
6. **大列表在库里筛选分页**：会员（带余额）、账户、预约历史改为服务端搜索分页，网页后台和小程序随之更新。
7. **运维**：外部可用性探测与备份新鲜度检查（GitHub Actions 定时任务，失败发邮件），异地备份等对象存储凭据到位后接上。

## 代码约定

- 处理函数通过请求事务（`txn`）读写数据：`q.order(id)` 这类方法按需从库里读出并放进本次请求的工作集，同一条记录在一个请求里只有一个实例；改完不用手动保存，事务提交前按 JSON 比较找出变化的记录写回（新建的用 `q.add…`）。查询前会先把已改动的记录写回，保证查到的是最新的。
- 业务历史不删除；撤销员工任命、作废会话、清理过期幂等记录走专门的方法。
- 推送的「影响到哪些顾客」由写回时自动收集（记录写回前后的归属账户），不在各接口里登记。
- 微信等外部调用一律在事务之外完成，事务重试时不会重复调用。
- 测试一律连真实 PostgreSQL（每个测试一个从模板复制的独立库）；没配测试库时测试失败而不是跳过，确实无关时用 `PINDOU_SKIP_DATABASE_TESTS=1` 显式跳过。
